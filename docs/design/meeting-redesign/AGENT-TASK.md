# 给原项目开发 agent 的任务说明

以下正文可以直接作为实施任务发送。将交付包放在附件中，或解压到当前仓库的 `docs/design/meeting-redesign/`。

---

请在当前 `meeting-recorder` 项目中，将附件交付包（或 `docs/design/meeting-redesign/`）里已确认的前端设计落地到现有 React / Electron 应用。

先阅读交付包的 README、`docs/design-baseline.md`、`docs/integration-map.md`、`docs/implementation-plan.md` 和 `docs/acceptance.md`，并核对当前仓库的 AGENTS.md、代码、未提交改动和现有测试。`source-baseline.json` 是整理包时的参考快照，当前仓库若有变化，以当前真实接口为准并记录差异。

目标：迁移五个页面的视觉语言与布局，同时复用现有录音、录屏、转录、分析、原文引用、项目记录、模型配置和本地数据库能力。HTML 是设计参考，应拆成适合现有项目的 React 组件，不能把原型 HTML 当成正式应用入口直接替换。

必须保留：

- 已确认的六个颜色变量、字体栈、轻灰外框、白色工作区、石墨色会议速览，以及各页面的视觉层次。
- 现有 React / Electron 技术栈、typed IPC、数据库、密钥保存方式、录制采集和媒体路径协议。
- 人工确认后才形成项目记录的规则；原文版本、历史分析、画面版本和引用解析规则。
- 原应用已有的自动统一说话人、模板管理、分析版本选择、导出、备份恢复、录屏及失败重试能力，即使设计稿没有逐一演示。

不能把原型的内置测试会议、静态问答、localStorage / IndexedDB 业务数据、浏览器录音实现、原型 JSON 备份或中文状态字符串直接搬进正式业务层。真实数据和保存结果必须来自现有业务接口。

先提出简短实施计划，然后开始落地。按交付包顺序先完成应用框架、会议库和会议详情，再迁移项目追踪、问答、模板与设置。允许为接入独立导航重构前端状态和组件，不为这次视觉迁移重写数据库、服务或录制引擎。

对 `docs/integration-map.md` 标记的接口缺口，首批交付以现有真实能力为边界：保留可用的只读、人工确认和历史查看流程，明确记录设计差异。不要虚构请求类型、用浏览器状态冒充后端保存，或静默扩展业务权限。新增项目记录编辑 API 应作为单独的业务扩展提案。

每批交付可运行的实际应用界面和对应验证结果。沿用当前仓库的构建、格式、单元测试和适用的 Electron 测试；不要为绕过失败删除测试或降级已有行为。真实会议和真实模型服务验证使用独立测试库及明确提供的测试资料。不要自动发布、推送标签或上传会议资料。

完成时说明：迁移了哪些页面、如何接入现有接口、通过哪些检查、哪些真实设备或服务场景尚未验证，以及剩余的设计／能力差异。
