## 保持 GitLab CI 的边界

初轮文件审查保留了原 CI；后续按用户确认的第一种路径调整同步任务。GitLab 继续开发、构建和发布，Windows 发布逻辑、版本号及既有标签保持不变，GitHub Actions 继续停用。上游域名、公共仓库标识及 Runner 标签作为工作流说明保留。

新的公共同步使用独立部署密钥及 `github-public` 环境变量：`GITHUB_PUBLIC_SSH_KEY_B64`、`GITHUB_PUBLIC_KNOWN_HOSTS`、`GITHUB_PUBLIC_ROOT`。旧镜像密钥不授权新仓库；旧流水线即使重试，也不能向新仓库复制原始历史。密钥值不进入 Git 或日志。

**原 `github_mirror` 会同步所有分支和标签，包括旧提交。** 现已改为默认分支验证通过后，逐文件导出到独立 Git 库，用 noreply 身份追加公共快照；固定公共根提交，不复制源提交对象或标签。相同内容不重复提交，旧流水线不会回退公共内容，意外根提交、分支、标签及下游独立作者都会使同步失败。

导出前检查私人文件路径、主目录、邮箱及内网地址；二进制必须命中人工审核的 SHA-256 清单，随后运行固定版本 Gitleaks。未知二进制、符号链接或扫描失败均阻止推送。自动检查仍不能代替对新增资料内容的人工审阅。

## 历史信息的两种处理路径

| 目标                                        | 方式                                                                                                                   | 对现有流程的影响                                                                                               |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 保持 GitLab 历史与 Release 不变，隐藏旧信息 | 从审查后的文件建立不继承旧历史的公共下游，或对下游做持续、确定性的历史过滤；公开前切换镜像逻辑并处理下游旧分支及标签。 | GitLab 构建和发布可保留，但必须修改同步任务。当前自动镜像不能继续向干净下游推送原始全部 refs。                 |
| 保留完全相同的全量 Git 镜像                 | 接受旧元数据及部署信息会公开，或协调两端重写历史并处理所有旧标签。                                                     | 重写会改变提交 ID，涉及已发布标签和 Release 溯源，与当前不移动已发布标签的约定冲突，不应在本次文件清理中执行。 |

已选择第一种路径，以新仓库和独立快照链保留 GitLab 发布历史。仅创建新分支、只推当前分支或重建 GitHub 仓库后继续使用原镜像，都不足以隔离旧历史。公共提交使用固定的 GitHub noreply 邮箱，未来上游提交也宜使用希望公开的身份。

GitHub 对历史清理、克隆和 fork 残留的说明见[官方文档](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。
