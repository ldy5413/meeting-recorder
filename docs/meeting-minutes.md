# 全场纪要与详细分析

会议分析分为两个阅读层次。默认的「会议纪要」先展示全场总览，再按所选模板呈现主要进展、决定、行动和未解决问题。「详细分析」保留已有的逐条事实、参数条件、原文和画面引用。

## 使用

- 新建分析完成详细事实提取和审核后，自动启动独立的全场提炼任务。提炼失败时详细分析仍然可用，可以单独重试。
- 已有报告在「会议纪要」中点击「生成全场纪要」，复用该份详细分析，不重新转录或识别画面。
- 在「提炼设置」中选择模板、语言和重点，再次提炼会增加纪要版本。自动语言沿用源详细分析的语言。原文、引用和源报告保持原样。
- 「查看依据」展开对应的详细条目，继续点击原文或画面引用可回听、查看历史截图。待办与决策仍从对应的详细条目人工确认进入项目记录；合并后的纪要不会自动创建项目事项。
- 会议库速览使用最新有效纪要的总览。没有纪要的历史会议可以主动生成；原文或画面改变后旧纪要会提示过期。
- 总览位于版本和导出工具之前。阅读报告时录像播放器默认缩小，可随时展开；进入「录像与画面」显示完整播放器，展开和收起保留播放位置。
- Markdown 可选择「仅导出纪要」或「包含详细分析与证据」。完整导出包含从纪要到详细条目的链接及截图附件；简短导出不附转录或截图。SRT 保持原文。完整备份保留全部纪要版本及审计数据。

## 提炼与核对

1. 读取完整的已审核详细条目，保留发言来源、原条目编号和决策／待办分类。
2. 分批确定会议重点，将关键议题与仅供深入阅读的资料区分开；每个原始编号都必须被归入其中一类。明确待办、决策必须进入重点。
3. 超出上下文预算时分批归并，再按模板综合全场内容。总览通常为一至两条短段落；正文合并同一主题，允许多条来源共同支撑一个要点。
4. 程序检查来源编号、明确待办和决策覆盖、章节深度及篇幅。周会由程序构建人员及进展／计划／阻塞子栏目；匿名编号只表示发言来源，纯画面和混合来源不能猜测人员。
5. 单独调用模型，按原始详细条目及其逐字引文审核每条纪要与章节标题。再分批检查全场重点覆盖。审核不通过时带反馈重新生成，至多三轮；单次调用的格式修复仍最多重试一次。
6. 全部通过后保存独立纪要版本。成功的中间步骤可续用；被否决的草稿不会永久缓存为重试结果。取消或源版本变化不会落库新纪要。

只有展示资料支持的要点会标为画面观察。程序拒绝将这类条目或讨论建议放入正式决策章节，也会拒绝将未确认的匿名说话人直接写成待办负责人。

这些检查不构成事实正确性的保证。详细分析自身可能存在转录、术语、数字或归属错误，模型审核也可能误判；重要结论仍应展开依据核对。概要可以省略辅助参数，但保留在概要里的数字及结果不能丢失影响解释的限定条件。

## 验证

`tests/minutes.test.ts` 验证来源、归属、覆盖、独立版本、语言和设置冻结、取消、续跑、自动提炼、长会议分批以及导出／备份。`tests/e2e/minutes.spec.ts` 验证桌面默认阅读、重试、更换模板、证据展开、历史选择、导出和中英文界面。

显式使用已授权的现有会议进行真实模型验证：

```powershell
npx tsx scripts/validate-minutes.ts --output=.local/minutes-validation/review
```

脚本只读打开安装版会议库，在 `.local/` 建立独立数据库副本，使用原先配置且已授权的分析服务。输出包括逐场 Markdown、统计报告及审计记录；它不修改正式会议数据，不重新发送音视频或原始截图。可使用 `--meeting=<会议ID>` 选择一场，`--rerun` 保留旧结果并重新生成。内部会议及生成内容不进入 Git。

2026-09-09 使用三场现有会议完成真实模型验证：详细条目分别为 144、118、118 条，提炼为 17、12、26 个要点（含总览）；正文分别由 19,465、19,885、21,561 字符缩短为 1,006、701、1,465 字符。三场通过程序与模型审核，源会议数据前后核对一致。该样本验证实际流程与可读篇幅，不用于估算事实准确率。
