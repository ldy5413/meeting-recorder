# 本机会议与 vLLM 接入验证

应用设置：填写自己的分析 Base URL、模型名及服务要求的 API Key。历史测试上下文预算为 `65536`；服务发现返回最大模型长度 `262144`，应用采用更保守的预算，并分批分析。公开版本省略实际部署地址、模型目录、个人路径及会议日期；以下使用匿名样本标识，保留原有测试指标与限制。

HTTP 支持本机与 RFC1918 私网 IPv4（10/8、172.16/12、192.168/16）。公网地址仍要求 HTTPS；不允许 URL 内嵌凭据、查询或片段。录音交给本机转录服务，分析接口接收转录文字、已有项目记录、问题与必要引用，不接收录音。

## 可重复的真实服务验证

在项目根目录执行：

```powershell
# 示例占位值：替换为自己的服务和已授权的资料目录。
$env:VLLM_BASE_URL = 'https://llm.example.com/v1'
$env:VLLM_MODEL = 'your-model-id'
npx tsx scripts/vllm-validation.ts '.local/inputs/meeting-a' '.local/inputs/meeting-b'
```

脚本只读原目录，创建独立 SQLite 库，完整导入两个目录中已有的 Meetily `transcripts.json`，运行应用真实分析任务、逐字证据校验与项目问答。这里的输入不是 VibeVoice 转录结果，不能用于衡量 VibeVoice 准确率。所有原文、模型输出和数据库只写入已被 Git 忽略的 `.local/vllm-validation/<时间戳>/`。`report.json` 记录段数、状态、耗时、结果与证据数量，`answer.json` 保存私密问答正文。

### 首轮语义抽查与修正

上述数字为**修改前基线**，不能据此宣称分析质量通过。人工逐项对照首轮两场各 6 项决策、待办或建议及其引用：两场各发现 3 项需要修正或进一步确认。第一场发现单方意见升级为决定、称呼被误当负责人、寒暄被误当有期限的待办；第二场发现负责人代词关联不明、讨论建议升级为决定、结束讨论被误写为工作完成。另见识别错词被模型具体化的风险。未进行全量人工标注，因此不计算召回率。

已收紧生成规则，并增加独立的一轮模型逐项审核：每项必须返回支持与否以及理由，不支持的条目不进入最终分析；审核缺项或索引重复会使任务失败。生成原文与审核原文保留在分析 checkpoint 的 `generationRaw` 和 `verificationRaw`，全部响应还保留在数据库 `meta` 表的 `analysis-audit:*` 条目中，便于失败诊断及备份迁移。不会改写原始模型输出。旧版未审核的未完成 checkpoint 在重试时会重新生成。

同一模型的二次审核只能降低风险，不能代替人工校对。正式待办与决策仍需用户确认。

真实长批次审核曾因理由过长触发输出截断，现限制每条理由最多40字；失败批次可用原 checkpoint 重试。问答正文限制为600字、最多6条引用、每条引用最多80字，分批和汇总均要求去重压缩，以避免宽泛问题把所有候选内容逐段复述导致截断。所有长度限制仍以模型实际输出及严格解析为准，遇到异常保留失败状态而不展示半成品。

恢复已有验证库（不要对正在被另一个 runner 使用的库执行）：

```powershell
npx tsx scripts/vllm-resume.ts .local/vllm-validation/<原运行时间戳>
```

## 协议兼容

2026-09-04 已访问真实 `/v1/models` 与 `/v1/chat/completions`；公开记录省略内部服务指纹。`response_format: {type: "json_object"}` 请求成功，返回正常 JSON 文本，`reasoning` 为 null。无需给所有 Chat Completions 提供商强加 vLLM 专用参数。

真实输出长度探针（16 tokens）返回 `finish_reason: "length"` 与不完整 JSON。应用在解析前拒绝截断，不保存半成品分析。已增加回归测试：独立 reasoning 字段不被当作答案、截断即使恰好为完整 JSON 也拒绝、非法 JSON 拒绝、仅有 reasoning 而无 content 拒绝。

如之后在服务器开启 Qwen thinking，可按 [vLLM 官方说明](https://docs.vllm.ai/en/stable/features/reasoning_outputs/) 设置服务端 `enable_thinking` 默认值。当前实际部署不需要这一调整。

证据校验通过仅代表引用 ID 和逐字文本存在、负责人和期限直接出现在引用中；不等同于人工验收决策/待办召回率达到 90%，也不证明模型对语义的每次判断正确。

## 真实 VibeVoice 录音闭环验收

`scripts/validate-live-meetings.ts` 从当前开发版受限 bridge 只读等待两场真实 VibeVoice 转录任务；不创建、重试或取消转录。任一场转录完成后，将目标两场归入独立验收项目，优先分析已完成的场次，另一场继续等待转录；两场分析结束后执行宽泛跨会议问答。这样可避免同项目已有 Meetily 转录混入此次验收。私密结果写入 `.local/live-vibevoice-validation/<时间戳>/`，不会输出 bridge 凭据。

本轮本机 ASR 运行期间实测存在 NVIDIA `SW Thermal Slowdown: Active`，核心频率曾降至约705MHz。分析服务使用远程 vLLM，但本机转录耗时受到热降频、窗口重试及部署配置调整影响，不能视为稳定性能基线。最终统计需区分实际 VibeVoice 输出与上文的已有 Meetily 文字测试。

第二场真实 VibeVoice 转录已完成：254段，末尾1860.021333秒。远程分析5批、127.16秒，19候选经审核剔除4项，最终15项、42处有效引用；均通过结构、引用和owner/due字面证据检查。数据保存在 `.local/live-vibevoice-validation/2026-09-05T01-40-02-554Z/`。

对这场真实VibeVoice结果另抽查6项决策/待办/建议，3项仍需校对：不完整引文不足以支持具体行动、把文档格式讨论错误具体化为实验工具、把带条件的讨论写成更确定的阶段安排。所有结果的owner和due均为空，未观察到把议题结束写成完成状态。此小样本不是全量人工标注，也不是90%召回率验收。

第一场真实VibeVoice转录完成562段、末尾3303.621333秒。首次分析以及明确单片段引用规则后的重试，均发现模型将相邻片段拼接为单个quote而被严格拒绝；同轮宽泛跨会议问答亦因无效引用拒绝返回。

为处理这种真实失败，分析和问答新增最多一次有界反馈重试：提供相同原文、失败输出及校验错误要求纠正，随后仍执行相同严格检查；不自动改写引用，也不接受无效结果。每次模型原响应及错误均保存在本地 `meta` 表 `grounding-audit:*` 中，最终分析checkpoint引用对应审计ID。真实HTTP回归验证纠正成功、二次失败即停止及失败raw保留；完整Node测试16项通过。

仅泛化错误提示不足以纠正错ID，最终反馈还提供具体错误引用、该ID实际原文与同批逐字匹配候选ID；模型重新生成后仍须通过相同严格校验。加入定位信息后，第一场真实VibeVoice分析完成11批，本次成功运行434.603秒，61候选剔除7项，最终54项、109处有效引用。该时间不含此前失败请求与本机ASR耗时。最终结果及审计见同目录 `july-final.json` 与本地数据库。

第一场另抽查6项决策/待办/建议，至少3项仍需人工确认：行动描述补入所选引文未包含的背景、已有实验做法被归类为新决定、含糊数量或范围被写得更确定。全部owner/due为空，全部change为new；不宣称达到无幻觉或90%召回率验收。

最终源码还在收到服务JSON响应后、检查内容格式与截断之前保存 `chat-audit:*`，覆盖合法服务JSON中包含的非法答案JSON、缺失content或length截断响应。HTTP失败、网络失败或服务返回本身并非JSON的情况不保证有响应正文审计。

宽泛跨会议问答的一次验证在约307秒出现Node验证客户端 `fetch failed`，当时服务端审计仍有成功模型响应。`AbortSignal.timeout(900000)` 未延长Node fetch底层等待响应头的默认限制，因此两份bridge验证脚本已改为 `node:http` 并显式设置900秒超时。桌面端走Electron IPC；开发浏览器走Chromium fetch，源码未设置同类Node fetch超时。此次客户端传输异常不能直接记为模型失败，也不能把中间批次当作最终问答成功。

最终以同一个宽泛问题重试完整请求成功：检索436个候选片段、17批及后续层级汇总，419.876秒后收到最终答案，22处引用来自2场真实VibeVoice会议；全部引用ID及逐字文本严格检查通过。模型最终未遵守prompt中的6引用上限，因此该上限仅是输出指导、不是接口硬约束；本次未发生截断。`answer-final.json` 保存最终答案，`final-report.json` 保存最终统计。没有重做已经成功的July分析，434.603秒仍为此前成功分析运行的耗时。

至此两场真实音频的转录、分析及宽泛跨会议问答服务闭环均已实际完成。结构与引用检查通过，语义抽查仍存在上文记录的问题；正式记录继续要求人工确认。Orca最终真实VibeVoice界面复验另受浏览器自动化 `runtime_unavailable` 影响，不因此宣称最终UI实测通过。
